# Telegram slash confirmation anchor and GroupChat startup status

This block publishes the accepted two-file native source correction for the confirmation-card defect recorded in the [preceding checkpoint](../native-new-conversation-boundary/README.md). It is based on native source 111 and is intended for a later integration. At source acceptance the correction was **not installed**; this publication performs no installation or service check and establishes no live or semantic acceptance. Full product scope remains open.

The gateway validates the Telegram confirmation anchor against the requesting message before metadata conversion. It refuses missing, malformed, boolean, foreign or oversized anchors and removes the newly registered pending confirmation that could not be shown safely. For a plain private chat it supplies the actual request message as an explicit reply anchor and preserves profile metadata. The Telegram adapter carries that explicit anchor through the confirmation prompt send path. The optional argument defaults to `None` for other prompt callers. Existing forum-topic routing, structured decline teardown, pending lifetime, callback payloads, ordinary sends and the strict receiver remain unchanged.

The accepted evidence records 46 scoped source controls and independent final review, including the original defect reproduction and invalid-anchor cases. Those unchanged results are reused here; they were not rerun. The controls used isolated transport recording, not Telegram transport. No destructive confirmation callback was invoked. This publication separately verifies the exact patch on the pinned source-111 beforeimages: zero-fuzz application produces byte-identical accepted source, both Python files parse, and reverse application restores the original bytes. The temporary verification copy is removed. The [manifest](patch-manifest.json) pins the patch, each before/after file and the acceptance evidence; [STATUS.json](STATUS.json) separates these facts.

The preceding actual request remains a consumed attempt: its card lacked a reply-to-request reference and the strict receiver accepted no bound card. No approval was sent, and no new-conversation boundary, reset or durable-memory recall was established. This source correction does not revise that actual outcome, clear the original UNKNOWN or authorize replay of an old attempt. Installation and a separately admitted current-instance user test remain necessary to establish the correction in the product.

A separate scoped investigation confirms the hosted GroupChat startup gap. Startup imports the CLI-authenticated TUI facade; that facade requires a retained authenticated CLI principal and exact user/profile admission. The background room/task adapter retains coordination fields, but it does not retain an admitted product `UserScope` and admission generation. Consequently there is no existing trusted internal entry contract that authorizes the room backend. The actual startup refusal is preserved; no GroupChat product patch was produced. Five isolated source-path and guard controls plus one schema control passed, with independent static review. These controls do not establish successful hosted-room startup or current operator intent; actual installed configuration was not read by that investigation.

A repair needs an explicit authenticated delegation from the product user to the exact room/member task and target profile, retained and rechecked across background execution, session/history/approval operations and cancellation. Import rewiring, a borrowed CLI grant, a missing-principal exemption or catching the refusal as success would not supply that authority. Direct unbound TUI refusal, foreign-profile refusal and revocation remain required. This unresolved feature gap is reported separately from the accepted Telegram source correction. Raw transcripts, answer oracles, credentials, user/chat/session identifiers, host paths and private handoffs are excluded from the public package.
