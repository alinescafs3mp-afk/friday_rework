# Protected native user onboarding

This is a source/offline component awaiting independent review and joined
installation. It does not establish the six mandatory live journeys or complete
ordinary capabilities. Astra owns integration of the separate admin-controls
candidate and the final installation. The intact donor catalogue remains required.

The existing authenticated Friday Dashboard now prepares a new private native
profile, captures its own credentials through Hermes' credential lifecycle,
approves native pairing and activates the completed setup. Every route retains
native signed sessions, operator verification, expiration, organization checks,
CSRF/origin handling and profile restrictions. Channel-admin roles do not grant
Dashboard authority. API schemas reject extra fields and noninteger generations.
No new user, history, task or administrative database is introduced.

A product principal is the exact platform, receiving transport profile, configured
account and user ID. Chat, topic, session and display name never replace it.
Two users in one chat route independently; the same user ID on another platform
or account has a different principal. Preparation refuses an existing principal,
binding, directory, symlink or ambiguous user route. It preserves existing config,
users, histories, job ownership, deadlines and stop records.

Preparation checks the supplied config SHA under the existing admission lock and
native process config lock. It commits a disabled native PluginState grant first,
then adds the exact native user route, binding, account runtime profile and admin
inspection profile using the native comment-preserving config writer. Native
`provision_new_home(..., publish=False)` creates only an exclusive new home; its
user capability marker remains absent. Fresh private memory/workspace directories
and the packaged reviewed Friday SOUL are installed without cloning any owner
history, instructions, skills, keys or context. Hermes may create empty native
infrastructure directories during credential capture.

The primary multiplex gateway reads the current protected onboarding routes at
its existing per-event resolver, before deriving a runtime identity. A stale
in-memory route list cannot enable the wrong profile or silently omit a newly
prepared route. Native served-profile resolution and grant checks remain in place.
A receiving profile that is not this gateway's primary routing authority is
explicitly refused: its compound primary/secondary config CAS join is still
required, rather than publishing a false routing success. Existing secondary
accounts and routes are retained.

Credentials are supplied explicitly to the new disabled profile, by required
native environment-name handles. The secret-valued API body uses SecretStr and
returns no value. The native protected writer and a home-stamped local secret
scope confirm persistence; process credentials are neither copied nor unioned.
Missing keys or native pairing leave an explicit disabled state. Secret sources,
ambient interpolation, inline keys, cloud inference/fallbacks and authority imports
are refused in the template. Paid Exa is the currently connected approved web
profile; other retained donor providers still need their audited template joins.

Activation checks the original principal/binding, current grant generation,
config/persona hashes, actual directory identity, credential presence and committed
route. Only then does it publish the native scope marker and enable the native
grant. That marker also binds the preparation receipt by SHA. Removing or replacing
the receipt, config, persona, private credentials, directory, binding or route
refuses actual native channel admission. Generic admin enable cannot bypass
incomplete onboarding. Native pairing approval can establish its separate grant
while the product profile stays disabled. Later revocation advances the native
generation; re-enable cannot revive a retained turn/job or reset its budget.

`GET /onboarding` reads disabled preparation records from existing bindings and
PluginState. The UI can continue the same verified prepared home after reload,
with its original generation. It never adopts an unknown or partially written
home. Incomplete writes remain disabled and require factual inspection; no automatic
retry erases uncertain state. Supported UI writes share the admission lock;
privileged external config edits must occur at a reconciled installation boundary
and are caught by the next file CAS and per-event route/setup validation.

## Explicit installation inputs

The normal installer must supply `plugins.entries.friday_rework.settings.onboarding.templates`
in the primary receiving home. Each approved name contains `config`, `tools` and
`required_secrets`. This source does not select an unverified production endpoint,
copy an ambient key or make an online discovery request. Missing templates are
reported as `INSTALLATION_INPUT_MISSING`.

The full nonsecret native config explicitly selects the existing observed local
model/provider/endpoint and capacities, empty inference fallbacks, every enabled
auxiliary and delegated local model route, memory/user context, approved useful
web settings, CLI and receiving-platform toolsets, trusted Friday/web plugins,
`allow_gateway_work/control` and enabled result hooks. The packaged RESEARCH text
must match the approved additive environment hint; SOUL remains the reviewed
Friday persona. No permanent 40960/4096 limit is introduced. Only the previously
reviewed eight ordinary capability names are admitted by the existing user scope;
other required native skills/browser/provider surfaces remain unaccepted, with no
catalogue deletion or waiver.

The existing worker runtime setting is retained explicitly. A disabled or missing
worker runtime is reported as requiring its existing readiness hooks, never as a
working Harness/A0 job. Enabled worker configuration must be installation-owned
and scoped to the new profile through the existing runtime receipts and checks.
Both intact workers, autonomous mid-task web, remaining ordinary capabilities,
primary/secondary onboarding joins and all six live journeys still require joined
installation and acceptance. This component does not move that assembly work to
the product user. A0 G3 reconciliation/STOP_UNCONFIRMED is unchanged; no A0 effect
is authorized here.

Apply `user-onboarding.patch` only after the exact accepted `user-isolation.patch`
identified by its manifest. It changes two native files and keeps the other 19
privacy overlay files unchanged. Future legitimate config/persona changes must
revalidate the managed setup receipt through a coordinated supported writer;
otherwise native admission refuses stale setup. This receipt join must be retained
when Astra composes the independently reviewed admin-controls candidate.
