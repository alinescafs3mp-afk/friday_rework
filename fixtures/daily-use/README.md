# Representative daily-use data — source preparation only

Version 1 contains twelve planned cases in `fixtures/daily-use/tasks.json`.
Every case is **NOT_RUN**. This is reusable data for later actual preparation,
not a runner, new task store, execution grant, benchmark or product acceptance.
Astra owns review, integration, final task selection and runtime admission.

| Case | Expected evidence/outcome |
| --- | --- |
| Telegram settings question | Grounded answer from the existing supplied settings bytes |
| Current urllib3 research | Actually read official sources and a version-aware answer, or honest retrieval failure |
| Short Harness calculator repair | Exact original input, independent unchanged owner checks, diff and returned artifact |
| Long original repository continuation | **PENDING_REAL_TARGET**: real multi-file repository, original goal/tests/write scope/grant must first be selected |
| A0 engineering repair | Original app/CP1251 CSV, both settings faults, confined diff, four outputs and actual independent five-check result |
| Binary file return | Same 149 CSV bytes and original authorized destination |
| Owned-task status | Authoritative original association; no new worker |
| Stop active repair | Actual cessation or truthful STOP_UNCONFIRMED; retained partial artifacts |
| Stop queued retry | Stop dominates reconciliation and restart; no automatic revival |
| Recoverable delivery failure | Retry transfer of the same verified bytes, without rerunning the worker |
| Missing required attachment | Ask for the missing file/refuse; no fabricated repair or borrowed attachment |
| Worker failure | Original bounded failure or policy-admitted same-job recovery; uncertain effects never replay |

The short arithmetic fixture is intentionally small. It supplies neither a long
coding scenario nor sustained duration evidence. The long case names the actual
FRW-022 repository/continuation integration goal but has no authorized concrete
long repository/task fixture yet. Its null target and explicit dependency block
execution. Selecting it requires a real agreed multi-file goal and immutable
inputs/checks, not repetition, sleep or relabelling the arithmetic example.

`source-pins.json` binds 26 existing product/archive files to the actual intake
commit. Inputs and checkers are referenced byte-for-byte rather than copied or
modified. Engineering uses the original `brief.txt`, manifest and mapping; paths
in mapping remain templates until genuine current admission fills them.

Only the named user input files and the applicable brief reach the worker.
Owner tests, checkers, calibration corrections/reports, manifests and mapping
evidence stay owner-controlled and outside worker write grants. Engineering may
change only settings and generated outputs; the original app and binary CSV stay
immutable. The calculator's owner tests also stay immutable. Real ingress,
worker-visible snapshots, diagnosis, goal checking, artifact staging and delivery
receipts are still required; historical component calibration is not new evidence.

All per-task original runtime limits remain typed **PENDING_ORIGINAL_ADMISSION**.
The existing checker limits are recorded separately: two affinity entries, 1 GiB
address space and 3 CPU seconds **per subprocess**, 64 KiB files, 5-second outer
wall limit; the engineering app has a 3-second inner wall limit, and the host
checker reserves 0.25 seconds for forced cleanup. These are unchanged finite
oracle bounds, not job budgets, aggregate worker quotas or soak defaults. No
checker was executed by this preparation.

The soak duration, chat concurrency, arrival schedule, mix weights, sample
interval, baselines, latency thresholds and recovery policy remain explicitly
unchosen. Preserve the existing shared single heavy-worker admission slot across
Harness and A0; deployment chat/queue/load parameters require actual selection.
AC034 later requires at least one real gateway restart and one real worker
failure plus latency/resource trends and a complete original job outcome ledger.
AC040 later requires stops during repair and queued retry, followed by normal
reconciliation/restart and evidence of no revival. Empty observations are null,
not zero measurements. No 24/7 or throughput claim is made.

FRW-022/023/029, all seven installed journeys and four web journeys remain
unaccepted. The corpus preserves mandatory cumulative web/admin scope and all
current pause/cancel/STOP/consumed boundaries; it authorizes no exclusion or
retry of historical jobs. FRW-030 source data preparation is not FRW-030 live
acceptance. Independent review and later admitted observations remain necessary.

Data-only integrity check, after placing the reviewed package beside its pinned
inputs (supply the actual product and immutable directive roots):

```sh
python3 -I -S -B validation/validate_daily_data.py --product-root /path/to/Friday_rework --archive-root /path/to/Friday_rework_Astra_Sol_Directive_V2_2026-10-06
```

This checks category/reference coverage, all source and brief hashes, owner-only
separation, original engineering manifest/mapping joins, binary CSV/calibration
data consistency and explicit pending runtime fields. It parses JSON/CSV only;
it never imports a fixture checker, application or native worker. PASS means
data consistency only, with runtime truth unattested and independent review
required. A changed input requires fresh binding/review, not a stale PASS.

The corpus path defaults to the supplied product root. For a separate source proposal, pass `--corpus-root /path/to/proposal/fixtures/daily-use`. Every worker-visible source reference, including the original engineering brief, is checked against owner-only separation. Checker metadata is fixed to the reviewed original checker hashes and limits; it cannot supply a worker grant. Reads check the complete current directory path again after reading.
